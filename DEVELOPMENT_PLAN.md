# План дальнейшей разработки

## 1. Целевая архитектура

1. Текущее серверное решение основано на Firebase.
2. Источником истины на первом этапе остаётся Firebase.
3. Целевое направление развития backend:
   - собственный сервер на Dart Frog
   - база данных PostgreSQL
4. Для взаимодействия с новым сервером будет использоваться пакет `packages/finance_api_client`.
5. Синхронизация с Firebase сохраняется как резервный и страхующий контур.
6. Переходный сценарий работы:
   - пользователь авторизуется через Google
   - данные подтягиваются из Firebase на собственный сервер
   - на сервере строится сводная аналитика
7. Важное уточнение по ближайшему этапу:
   - требуется создать отдельный сайт на Flutter
   - сайт должен поддерживать авторизацию через Google
   - после авторизации должен запускаться сценарий загрузки данных из Firebase на собственный сервер
8. На текущем этапе доработка мобильного приложения не является приоритетом и не требуется, если только она не понадобится для поддержки migration flow.
9. Долгосрочная цель:
   - полный переход на собственный сервер
   - постепенное снижение зависимости от Firebase

## 2. Ближайший продуктовый фокус

1. Основной фокус разработки переносится с мобильного приложения на web-направление.
2. Приоритетный пользовательский сценарий:
   - пользователь открывает сайт
   - авторизуется через Google
   - подтверждает или запускает перенос данных
   - данные из Firebase загружаются на собственный сервер
   - после загрузки становятся доступны серверные данные и аналитика
3. Ближайшая цель проекта:
   - получить рабочий web-вход в систему
   - обеспечить первичную загрузку данных из Firebase
   - подготовить основу для аналитики на сервере
4. Доработки `apps/mobile` пока откладываются.

## 3. Новый Flutter-сайт

1. Создать отдельное Flutter Web-приложение в структуре монорепозитория.
2. Определить его роль:
   - входная точка для пользователя
   - запуск миграции данных
   - в дальнейшем интерфейс для просмотра сводной аналитики
3. Реализовать базовые страницы:
   - landing или стартовая страница
   - страница авторизации
   - страница статуса загрузки данных
   - страница результата импорта
   - базовая страница аналитики или dashboard-заглушка
4. Продумать пользовательский поток после входа:
   - проверка авторизации
   - получение данных профиля
   - запуск процесса миграции
   - отображение прогресса и результата
5. Сразу заложить архитектуру, пригодную для дальнейшего расширения:
   - авторизация
   - импорт данных
   - аналитика
   - настройки пользователя

## 4. Поток миграции данных из Firebase

1. Формально описать migration flow до начала активной реализации.
2. Определить, какие сущности должны переноситься в первую очередь:
   - пользователи
   - группы пользователей
   - счета
   - категории
   - операции
3. Зафиксировать, как будет запускаться перенос:
   - автоматически после входа
   - вручную по кнопке
   - комбинированный вариант
4. Определить, как сервер понимает, что данные уже были импортированы.
5. Определить стратегию повторной загрузки:
   - полный повторный импорт
   - инкрементальная синхронизация
   - смешанный сценарий
6. Зафиксировать правила консистентности:
   - как обрабатываются дубликаты
   - как обрабатываются удалённые записи
   - как разрешаются конфликты
   - как отслеживается актуальность данных
7. Определить, какие данные остаются только в Firebase на переходном этапе, а какие считаются продублированными на сервере.

## 5. Развитие серверной части

1. `apps/server` становится одним из основных направлений разработки.
2. Первый обязательный контур на сервере:
   - приём авторизованного пользователя
   - верификация Google/Firebase-аутентификации
   - создание или поиск пользователя на своей стороне
   - импорт данных из Firebase
   - сохранение данных в PostgreSQL
3. После этого нужен минимальный прикладной контур:
   - чтение импортированных данных
   - агрегирование данных
   - выдача сводной аналитики
4. Реализацию серверной части стоит вести по этапам:
   - аутентификация и регистрация
   - импорт данных
   - нормализация и сохранение
   - аналитические endpoint'ы
   - подготовка к полному переходу на свой backend
5. Нужно убрать или заменить все критичные незавершённые места:
   - `UnimplementedError`
   - пустые route handlers
   - временные ответы-заглушки
6. Конфигурация сервера должна быть сразу подготовлена для нормальной разработки:
   - переменные окружения
   - настройки подключения к PostgreSQL
   - секреты и ключи без хардкода

## 6. Контракты, модели и интеграции

1. Нужно привести к единой схеме следующие слои:
   - Firebase-модели и структура исходных данных
   - серверные модели в `apps/server`
   - DTO в `packages/dto_models`
   - клиент `packages/finance_api_client`
   - описание API в `api_spec.yaml`
2. Для migration flow особенно важно зафиксировать соответствие между:
   - полями в Firebase
   - полями в PostgreSQL
   - DTO для передачи по API
3. Необходимо определить единый источник истины для API-контрактов нового сервера.
4. Любые расхождения в именах, типах, nullable-полях и идентификаторах нужно устранить до активного расширения API.
5. `finance_api_client` должен развиваться как основной клиентский слой для нового backend-контра.

## 7. Инфраструктура и конфигурация

1. Подготовить удобный сценарий локального запуска нового web/server-контура.
2. Обновить документацию проекта под новую стратегию:
   - что является текущим продуктовым фокусом
   - как запускать Flutter Web
   - как запускать Dart Frog server
   - как поднимать PostgreSQL
   - как настраивать Firebase и Google auth
3. Исправить проблемы с кодировкой в markdown-файлах.
4. Убрать чувствительные данные из исходников.
5. Зафиксировать структуру конфигурации:
   - локальная разработка
   - тестовое окружение
   - production-подход на будущее

## 8. Тестирование и надёжность

1. Тестовый приоритет смещается на новый web/server-поток.
2. В первую очередь нужны тесты для:
   - серверной аутентификации
   - импорта данных из Firebase
   - маппинга Firebase -> server models -> DTO
   - аналитических расчётов
3. Для Flutter-сайта нужны проверки ключевых пользовательских сценариев:
   - вход через Google
   - запуск импорта
   - отображение статуса переноса
   - отображение результата
4. Для `finance_api_client` нужны тесты, подтверждающие корректность работы с новыми endpoint'ами.
5. После стабилизации базового потока стоит добавить автоматические проверки в CI.

## 9. Рекомендуемый порядок выполнения

1. Зафиксировать окончательно структуру нового web/server-сценария.
2. Создать отдельное Flutter Web-приложение и реализовать базовый вход через Google.
3. Подготовить серверную аутентификацию и приём пользователя на стороне Dart Frog.
4. Реализовать первичный импорт данных из Firebase в PostgreSQL.
5. Проверить целостность и читаемость импортированных данных.
6. Реализовать первые аналитические endpoint'ы и базовый dashboard на сайте.
7. После этого расширять серверный контур и готовить проект к полному переходу на свой backend.

## 10. Почему такой порядок

1. Ближайшая бизнес-задача связана не с мобильным приложением, а с переносом данных и построением аналитики через новый web/server-поток.
2. Без работающего сайта, через который пользователь сможет войти и инициировать перенос, нельзя проверить целевой пользовательский сценарий.
3. Без формального migration flow есть высокий риск дублирования логики, расхождения моделей и неконсистентных данных.
4. Сначала нужно обеспечить вход, импорт и сохранение данных, а уже затем строить расширенную аналитику и готовиться к полному отказу от Firebase.
