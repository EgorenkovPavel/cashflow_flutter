# План дальнейшей разработки

## 1. Целевая архитектура

1. Текущее серверное решение основано на Firebase.
2. Источником истины на первом этапе остаётся Firebase.
3. Целевое направление развития backend:
   - собственный сервер на Dart Frog
   - база данных PostgreSQL
4. Для взаимодействия с новым сервером будет использоваться пакет `packages/finance_api_client`.
5. Синхронизация с Firebase сохраняется как резервный и страхующий контур.
6. Переходный сценарий работы:
   - пользователь авторизуется через Google
   - данные подтягиваются из Firebase на собственный сервер
   - на сервере строится сводная аналитика
7. Важное уточнение по ближайшему этапу:
   - требуется создать отдельный сайт на Flutter
   - сайт должен поддерживать авторизацию через Google
   - после авторизации должен запускаться сценарий загрузки данных из Firebase на собственный сервер
8. На текущем этапе доработка мобильного приложения не является приоритетом и не требуется, если только она не понадобится для поддержки migration flow.
9. Долгосрочная цель:
   - полный переход на собственный сервер
   - постепенное снижение зависимости от Firebase

## 2. Ближайший продуктовый фокус

1. Основной фокус разработки переносится с мобильного приложения на web-направление.
2. Приоритетный пользовательский сценарий:
   - пользователь открывает сайт
   - авторизуется через Google
   - подтверждает или запускает перенос данных
   - данные из Firebase загружаются на собственный сервер
   - после загрузки становятся доступны серверные данные и аналитика
3. Ближайшая цель проекта:
   - получить рабочий web-вход в систему
   - обеспечить первичную загрузку данных из Firebase
   - подготовить основу для аналитики на сервере
4. Доработки `apps/mobile` пока откладываются.

## 5. Развитие серверной части

1. `apps/server` становится одним из основных направлений разработки.
2. Первый обязательный контур на сервере:
   - приём авторизованного пользователя
   - верификация Google/Firebase-аутентификации
   - создание или поиск пользователя на своей стороне
   - импорт данных из Firebase
   - сохранение данных в PostgreSQL
3. После этого нужен минимальный прикладной контур:
   - чтение импортированных данных
   - агрегирование данных
   - выдача сводной аналитики
4. Реализацию серверной части стоит вести по этапам:
   - аутентификация и регистрация
   - импорт данных
   - нормализация и сохранение
   - аналитические endpoint'ы
   - подготовка к полному переходу на свой backend
5. Нужно убрать или заменить все критичные незавершённые места:
   - `UnimplementedError`
   - пустые route handlers
   - временные ответы-заглушки
6. Конфигурация сервера должна быть сразу подготовлена для нормальной разработки:
   - переменные окружения
   - настройки подключения к PostgreSQL
   - секреты и ключи без хардкода

## 10. Почему такой порядок

1. Ближайшая бизнес-задача связана не с мобильным приложением, а с переносом данных и построением аналитики через новый web/server-поток.
2. Без работающего сайта, через который пользователь сможет войти и инициировать перенос, нельзя проверить целевой пользовательский сценарий.
3. Без формального migration flow есть высокий риск дублирования логики, расхождения моделей и неконсистентных данных.
4. Сначала нужно обеспечить вход, импорт и сохранение данных, а уже затем строить расширенную аналитику и готовиться к полному отказу от Firebase.

### 2026-06-03 — формат совместной работы

1. Проект анализируется итеративно.
2. Вопросы пользователю задаются по одному.
3. Все принятые договорённости и архитектурные решения фиксируются в этом файле.
4. Перед активной реализацией сначала уточняется ближайший продуктовый и технический приоритет.

### 2026-06-03 — текущее состояние проекта после первичного анализа

1. Репозиторий — Dart/Flutter монорепозиторий под управлением Melos.
2. Основные приложения:
   - `apps/mobile` — существующее мобильное Flutter-приложение с локальной БД, Firebase/Auth, Google Drive backup и доменной логикой финансов.
   - `apps/web_analytic` — новый Flutter Web-контур с базовой Firebase Google-аутентификацией.
   - `apps/server` — Dart Frog backend с PostgreSQL через Drift и начальным endpoint'ом регистрации пользователя.
3. Основные пакеты:
   - `packages/finance_models` — общие финансовые enum'ы и value-модели.
   - `packages/dto_models` — DTO-модели для API.
   - `packages/finance_api_client` — клиент нового backend API.
   - `packages/firebase_api_client` — клиент/мапперы текущего Firebase-контура.
4. `apps/web_analytic` уже умеет входить через Firebase Auth Google popup и показывать профиль пользователя, но пока не вызывает backend.
5. `apps/server` уже содержит `/register`, проверку Firebase ID token через `firebase_admin` и создание пользователя/группы в PostgreSQL.
6. Серверный слой данных пока неполный: accounts/categories/operations в `DataRepositoryImpl` в основном оставлены через `UnimplementedError`.
7. В проекте есть чувствительная/локальная конфигурация, которую нужно вынести из кода:
   - путь к Firebase service account в `apps/server/lib/firebase_service.dart`
   - пароль PostgreSQL в `apps/server/lib/data/database.dart`
   - Firebase Web config в `apps/web_analytic/lib/main.dart`
8. `api_spec.yaml` описывает только начальный контракт: `/register` и часть accounts API.
9. `DEVELOPMENT_PLAN.md` уже содержит стратегию перехода от Firebase к собственному Dart Frog/PostgreSQL backend через web/server migration flow.

### 2026-06-03 — ближайшая целевая задача

1. Нужно сделать так, чтобы `apps/web_analytic` мог отдать backend команду на загрузку данных из Firebase в серверную PostgreSQL БД.
2. После загрузки `apps/web_analytic` должен показывать данные уже из серверной БД, а не напрямую из Firebase.
3. Целевой пользовательский поток:
   - пользователь входит в `apps/web_analytic` через Google/Firebase Auth;
   - web-приложение получает Firebase ID token;
   - web-приложение вызывает backend;
   - backend верифицирует пользователя;
   - backend загружает данные пользователя из Firebase;
   - backend сохраняет импортированные данные в PostgreSQL;
   - web-приложение запрашивает данные через backend API;
   - web-приложение отображает данные из PostgreSQL.
4. Ближайшие технические блоки для проработки:
   - endpoint запуска импорта на backend;
   - статус/результат импорта;
   - чтение импортированных данных через backend;
   - отображение этих данных в `apps/web_analytic`;
   - защита всех вызовов Firebase ID token'ом.

### 2026-06-03 — решение по месту выполнения импорта

1. Импорт данных из Firebase должен выполняться полностью на backend в `apps/server`.
2. `apps/web_analytic` не должен читать финансовые данные из Firebase напрямую.
3. Роль `apps/web_analytic` в migration flow:
   - авторизовать пользователя через Firebase Auth;
   - получить Firebase ID token текущего пользователя;
   - отправить backend команду на запуск импорта;
   - показать статус и результат импорта;
   - после импорта читать данные только через backend API.
4. Роль `apps/server` в migration flow:
   - принять команду импорта;
   - проверить Firebase ID token;
   - определить или создать серверного пользователя;
   - прочитать нужные данные пользователя из Firebase;
   - преобразовать Firebase-модели в серверные модели;
   - сохранить данные в PostgreSQL;
   - предоставить API для чтения импортированных данных.

### 2026-06-03 — запуск импорта на первом этапе

1. На первом этапе импорт запускается вручную из `apps/web_analytic`.
2. После входа пользователя приложение должно показать отдельную кнопку запуска, например “Загрузить данные из Firebase”.
3. Нажатие кнопки отправляет backend команду на импорт с Firebase ID token текущего пользователя.
4. Автоматический запуск импорта сразу после входа пока не реализуется.
5. В дальнейшем сценарий запуска может измениться: ручной запуск считается временным решением первого этапа.

### 2026-06-03 — порядок переноса сущностей

1. Импорт реализуется поэтапно, а не сразу для всех сущностей.
2. Первая рабочая версия импорта переносит счета.
3. После счетов в дальнейшем должны быть добавлены остальные основные сущности:
   - категории;
   - операции;
   - группы пользователей и связанные пользовательские данные, если они потребуются для корректной модели.
4. Несмотря на узкий первый шаг, архитектура импорта должна сразу учитывать будущее расширение до полного переноса данных.
5. Первый backend endpoint импорта можно проектировать так, чтобы он запускал общий import flow, но на начальном этапе фактически выполнял только импорт счетов.

### 2026-06-03 — идентификаторы импортированных счетов

1. Для импортированных счетов в PostgreSQL используется собственный серверный UUID как основной `id`.
2. Исходный Firebase document ID счёта сохраняется отдельным полем, например `firebaseId` или `sourceFirebaseId`.
3. Firebase ID не должен становиться основным ключом серверной модели.
4. Для защиты от дублей при повторном импорте нужен уникальный ключ по паре:
   - `userGroupId`;
   - `firebaseId`.
5. Повторный импорт счетов должен находить существующую запись по `userGroupId + firebaseId` и обновлять её, а не создавать дубль.
6. Такой подход сохраняет связь с исходными Firebase-данными для миграции, но оставляет серверную модель независимой от Firebase в будущем.

### 2026-06-03 — стратегия повторного импорта счетов

1. В краткосрочной перспективе данные считаются приходящими только из Firebase.
2. Firebase на первом этапе является источником истины для импортируемых счетов.
3. При повторном импорте сервер должен полностью обновлять поля счёта значениями из Firebase.
4. Локальные изменения счёта на сервере на первом этапе не считаются отдельным источником изменений и могут быть перезаписаны импортом.
5. Технически импорт счетов должен работать как upsert:
   - если счёт с `userGroupId + firebaseId` уже есть — обновить его из Firebase;
   - если счёта нет — создать новую серверную запись.
6. В дальнейшем стратегия может измениться на более сложную: серверные изменения, конфликты, инкрементальная синхронизация или отказ от Firebase как источника истины.

### 2026-06-03 — отображение счетов в web после импорта

1. После импорта счетов `apps/web_analytic` на первом этапе должен показать простой список счетов из серверной PostgreSQL БД.
2. Список должен приходить через backend API, а не напрямую из Firebase.
3. Для первой версии не нужны балансы, операции, аналитика, фильтры или сложная визуализация.
4. В списке должны отображаться все поля счёта, доступные в серверной модели/API-ответе.

### 2026-06-03 — найденные поля счёта в текущем коде

1. Firebase-модель `CloudAccount` сейчас содержит:
   - `id`;
   - `title`;
   - `isDebt`;
   - `deleted`;
   - `userGoogleId`.
2. Мобильная domain-модель счёта использует:
   - `id`;
   - `cloudId`;
   - `title`;
   - `userId`;
   - вычисляемый `isDebt` через варианты `account`/`debt`.
3. Серверная модель `apps/server/lib/models/account.dart` сейчас содержит:
   - `id`;
   - `name`;
   - `isDebt`;
   - `userId`;
   - `groupId`.
4. DTO-модель `BaseAccountResponse` сейчас использует:
   - `id`;
   - `title`;
   - `userId`;
   - тип счёта через варианты `account`/`debt`.
5. Есть расхождение в названии поля счёта: `title` в Firebase/mobile/DTO против `name` в части server/API.
6. Для импорта нужно отдельно решить, переносится ли поле `deleted` в PostgreSQL и показывается ли оно в `apps/web_analytic`.

### 2026-06-03 — полнота импорта счетов

1. На первом этапе импортируем все данные счёта из Firebase, включая служебные поля.
2. Поле `deleted` должно переноситься в PostgreSQL.
3. Удалённые в Firebase счета не должны отфильтровываться на этапе импорта.
4. API чтения счетов должен позволять `apps/web_analytic` увидеть поле `deleted`.
5. `apps/web_analytic` на первом этапе показывает все импортированные счета, включая записи с `deleted = true`.

### 2026-06-03 — название поля счёта

1. Основное название пользовательского имени счёта в серверной модели и API — `title`.
2. Поле `name` для счёта не должно использоваться в новом контракте.
3. При доработке server/API нужно привести текущие места с `name` к `title`.
4. Это сохраняет соответствие Firebase-модели, мобильной domain-модели и DTO-модели.

### 2026-06-03 — endpoint запуска импорта

1. Для запуска переноса данных закладывается общий backend endpoint, а не специализированный endpoint только для счетов.
2. На первом этапе общий endpoint фактически импортирует только счета.
3. В дальнейшем этот же import flow должен быть расширен на остальные сущности:
   - категории;
   - операции;
   - другие связанные данные.
4. Предпочтительное направление контракта: один endpoint уровня `POST /import` или близкий по смыслу вариант.
5. `apps/web_analytic` должен вызывать общий endpoint импорта и не знать деталей о том, какие сущности уже поддержаны backend'ом.

### 2026-06-03 — терминология sync вместо import

1. В проекте для этого процесса используем термин `sync`.
2. Причина: процесс может запускаться повторно и обновлять уже загруженные данные из Firebase.
3. Endpoint запуска должен быть общим sync endpoint'ом, например `POST /sync`.
4. Старое слово `import` в плане означает начальную реализацию sync flow, но новые API/классы/экраны лучше называть через `sync`.
5. На первом этапе `sync` выполняет синхронизацию счетов из Firebase в PostgreSQL.

### 2026-06-03 — режим выполнения sync

1. На первом этапе `POST /sync` работает синхронно.
2. HTTP-запрос ждёт завершения синхронизации счетов из Firebase в PostgreSQL.
3. После завершения backend возвращает результат выполненной синхронизации.
4. Отдельный `syncJobId` и endpoint проверки статуса на первом этапе не нужны.
5. В дальнейшем, если sync станет долгим или появятся большие задержки, можно перейти на асинхронную схему:
   - `POST /sync` возвращает `syncJobId`;
   - отдельный endpoint отдаёт статус и результат sync job.

### 2026-06-03 — ответ `POST /sync`

1. `POST /sync` не должен возвращать список загруженных счетов.
2. Ответ `POST /sync` должен содержать статус выполнения sync.
3. Ответ должен содержать возможное описание ошибки, если sync завершился неуспешно или частично неуспешно.
4. Ответ должен содержать количество загруженных элементов.
5. На первом этапе под загруженными элементами подразумеваются счета.
6. Получение списка счетов выполняется отдельным действием в `apps/web_analytic`.
7. Для получения списка счетов нужен отдельный backend GET endpoint, который будет вызываться отдельной кнопкой в web-интерфейсе.

### 2026-06-03 — статусы sync на первом этапе

1. На первом этапе для `POST /sync` достаточно двух статусов:
   - `success`;
   - `error`.
2. Статус `partialSuccess` пока не нужен.
3. Если при синхронизации произошла ошибка, backend возвращает `error` и описание ошибки.
4. Если синхронизация счетов завершилась без ошибки, backend возвращает `success` и количество загруженных элементов.

### 2026-06-03 — определение рабочей группы пользователя

1. В `apps/web_analytic` пользователь авторизуется через Google/Firebase Auth.
2. Backend получает Firebase ID token и извлекает Google ID пользователя.
3. В данных Firebase группы содержат пользователей с Google ID.
4. По Google ID текущего пользователя backend должен найти группу пользователя.
5. Sync счетов должен загружать счета только из найденной группы.
6. После sync работа web/server-контура на первом этапе ведётся только с этой группой.
7. `apps/web_analytic` не должен предлагать выбор группы на первом этапе.
8. Backend сам определяет рабочую группу текущего пользователя по токену и данным Firebase.

### 2026-06-03 — неоднозначная группа пользователя

1. Если Google ID текущего пользователя найден в нескольких группах Firebase, это считается ошибкой.
2. Backend не должен автоматически выбирать первую найденную группу.
3. В такой ситуации sync должен завершиться со статусом `error`.
4. Описание ошибки должно объяснять, что пользователь найден более чем в одной группе.
5. На первом этапе UI выбора группы не реализуется.

### 2026-06-03 — отсутствие группы пользователя

1. Если Google ID текущего пользователя не найден ни в одной группе Firebase, это считается ошибкой.
2. Backend не должен создавать новую группу в рамках sync.
3. Sync должен завершиться со статусом `error`.
4. Описание ошибки должно объяснять, что группа пользователя в Firebase не найдена.
5. На первом этапе работа возможна только для пользователей, которые уже присутствуют в группе Firebase.

### 2026-06-03 — идентификаторы импортированных групп

1. Серверная `userGroup` в PostgreSQL должна иметь собственный серверный UUID как основной `id`.
2. Исходный Firebase ID группы должен сохраняться отдельным полем, например `firebaseId` или `sourceFirebaseId`.
3. Firebase ID группы не должен становиться основным ключом серверной модели.
4. При повторном sync backend должен находить существующую серверную группу по Firebase ID группы.
5. Если серверной группы с таким Firebase ID ещё нет, backend создаёт новую серверную группу и связывает её с Firebase ID.
6. Это нужно, чтобы повторный sync не создавал дубли групп.

### 2026-06-03 — перенос пользователей группы

1. При sync счетов backend должен переносить в PostgreSQL всех пользователей найденной Firebase-группы.
2. Нельзя ограничиваться только текущим авторизованным пользователем.
3. Группа пользователей переносится как рабочий контекст целиком.
4. После определения Firebase-группы по Google ID текущего пользователя backend должен:
   - создать или обновить серверную группу;
   - создать или обновить всех пользователей этой группы;
   - затем синхронизировать счета этой группы.
5. Связь пользователей с группой в PostgreSQL должна соответствовать найденной Firebase-группе.

### 2026-06-03 — дедупликация пользователей при sync

1. Пользователи в PostgreSQL должны иметь собственный серверный UUID как основной `id`.
2. Повторный sync должен дедуплицировать пользователей по паре:
   - `userGroupId`;
   - `googleId`.
3. Если пользователь с таким `userGroupId + googleId` уже есть, backend обновляет его поля из Firebase.
4. Если пользователя с таким `userGroupId + googleId` нет, backend создаёт новую серверную запись.
5. Это соответствует общему принципу sync: серверные UUID остаются внутренними идентификаторами, а внешние Firebase/Google ID используются для сопоставления импортируемых данных.

### 2026-06-03 — связь счёта с пользователем

1. Firebase-счёт содержит поле `userGoogleId`.
2. При sync backend должен связать счёт с серверным пользователем по `userGoogleId` внутри текущей серверной группы.
3. Для сопоставления используется пользователь с парой `userGroupId + googleId`.
4. Если для `userGoogleId` счёта не найден пользователь в текущей группе, это считается ошибкой данных.
5. В такой ситуации sync должен завершиться со статусом `error`.
6. Backend не должен создавать отдельного пользователя только на основании `userGoogleId` счёта, если такого пользователя нет среди пользователей найденной Firebase-группы.

### 2026-06-03 — общий счёт без владельца

1. Если у Firebase-счёта `userGoogleId == null`, это не считается ошибкой.
2. Такой счёт должен импортироваться в PostgreSQL без владельца.
3. Счёт без владельца трактуется как общий счёт для всех пользователей группы.
4. Серверная модель счёта должна допускать nullable `userId`.
5. При отображении в `apps/web_analytic` такой счёт должен быть виден в общем списке счетов группы.
